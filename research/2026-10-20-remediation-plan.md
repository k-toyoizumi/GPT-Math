## 4. 改修の具体的な設計

### 4.1 依存関係とCIの実行

- 当面はLean 4.24.0 / Mathlib v4.24.0を維持し、更新作業を混在させない。
- プロジェクトの `lake-manifest.json` を追跡し、Mathlibと推移依存の解決SHAを照合する。
- 依存gateのraw正規表現の二重エスケープを修正する。正常入力が通るテストを最初に追加する。
- 通常のCIを毎回の依存更新から分離する。採用manifestによる解決を使い、実行後にmanifest差分がないことを確認する。依存更新は独立した変更としてレビューする。
- 実行環境のLean/Lake/Pythonの版と実依存SHAをログへ残す。ビルドを行わない静的チェックの成功と、実環境での成功を分ける。
- `permissions: contents: read` を検証ジョブの基本とする。検証成果物の保存と、研究成果のcommit/pushの権限を混同しない。

### 4.2 Lean対象の網羅と草稿

追跡された全Leanファイルについて、「採用・通常CIで実行」「草稿・明示的に隔離」「設定ファイル等・理由付き対象外」のいずれかを台帳で指定する。未知の追加ファイルは黙って無視せず失敗とする。

Lakeライブラリのルートと配下モジュールを区別し、すべてのファイルを別々の `lean_lib` として登録する方式に依存しない。ライブラリのbuild対象・import経路・直接検査の対応を示し、各採用ソースの実行を確認する。

通常の `lake build` とCIでの採用範囲を合わせる。草稿を隔離している場合は、その理由と未検証状態をREADMEに表示する。全ファイルの個別コンパイルによる重複実行は、網羅性を保てる範囲で避ける。

`ProgressionCompleteness.lean` と `TypeIIDivisorComplete.lean` はまず固定環境でコンパイルし、失敗すれば修正する。動作確認前の名称変更だけで検証済み扱いにしない。

### 4.3 証明の信頼区分

| 区分 | 意味 | 必須の証拠 |
|---|---|---|
| paper-proof-only | 読み下せる証明はあるがLeanでは未証明 | 主張・仮定・導出・未形式化箇所 |
| kernel-checked | 通常のLeanカーネルによる検査。標準公理の依存を併記 | 固定ソース、成功run、全公理一覧 |
| native-assisted | native_decide等によりコンパイラ・実行系への信頼を追加 | 上記＋native由来の依存と使用箇所 |
| numerical-only | 有限計算・浮動小数点確認 | 範囲、手法、整数/有理数/近似の区別、出力 |
| draft | コンパイル・証明・再現が未完 | 次の検証工程と停止理由 |

これらと新規性・論文化価値を別欄にする。通常のLean標準公理を自作の仮定として誤分類しない。全採用定理について公理依存を取得し、`sorryAx` や許可されていない自作公理を拒否する。文字列grepは補助に留める。

### 4.4 Pythonと有限証明書

- mainの既存2本を、そのまま再現基準としてCIに組み込む。
- p=670849の因数分解による約数生成と、平方根までの試し割り・合同数列列挙を照合する既存検証を接続する。
- 素数性、正の分母、交差積、有理数等式をチェックし、証人の正しさと探索の完全性を別々に記録する。
- 最小・境界・空集合・範囲外・off-by-oneの異常系を追加する。現実的な時間内に終わる小さいテスト範囲を通常CIに使う。
- 実験結果の期待値を変更するときは、その数学的理由と独立再計算を必要とする。assertを消して成功にしない。

### 4.5 故障注入の受け入れテスト

以下は隔離fixtureまたは専用の検証用変更で実施する。通常の研究ブランチに故意の不正証明を残さない。

| 入れる不具合 | 期待する検出結果 |
|---|---|
| 未登録の追跡Leanファイルを追加 | inventory/coverage失敗 |
| 採用対象にコンパイル不能なLeanを追加 | Lean工程失敗 |
| `sorry` で閉じた定理・許可外公理への依存 | proof trust工程失敗 |
| 正常なLean/Mathlib版・manifest | 依存gate成功 |
| manifest欠損、版不一致、SHA改変 | 依存gate失敗 |
| Pythonの期待式または証人を1か所破損 | Python工程失敗 |
| tee等を経由するコマンドの失敗 | ログを保存してもjobが失敗のまま |
| 証拠の生成漏れ・対象SHA不一致 | artifact検査または結果台帳の照合で失敗 |

ローカルの単体テスト成功に加え、GitHub Actionsの実ジョブで検出された証拠を残す。故意に失敗させたrunは、その目的と期待結果を明示する。

### 4.6 証拠保存と台帳

最低限、以下をCI成果物として保存する。

- `run.json`：source SHA、検証したtree、run ID、attempt、時刻、イベント、実コマンド、環境版、各工程の終了状態。
- `proofs.json`：定理名、statement hash、ソースpath、ソースblob SHA、信頼区分、公理依存、検証run。
- `experiments.json` と証明書CSV：入力・範囲・アルゴリズム・結果・整数/有理数/近似の区別。
- `coverage.json`：追跡Lean一覧、採用/草稿/対象外、実際の検証経路。
- 実行ログと `SHA256SUMS`：ハッシュ一覧は自分自身を対象外とする。

PR実行では検証したmerge SHAとPR head SHAを区別する。実験・証明の内容を変更した後、以前の成功runを新しい内容の証拠に流用しない。artifact自身は保持期間を持つため、期限前に必要な証拠を永続的な研究記録へ移す運用を定める。

成果物保存は可能な範囲で `always()` 相当の条件で実行する。取得失敗・強制終了などで証拠を残せない場合は「証拠なし」とし、成功を推定しない。保存に成功しても検証の失敗を成功へ変換しない。

### 4.7 Agentの継続性と書き込み失敗

1回の実行にtask ID、目的、開始SHA、次の最小検証、結果、停止理由、次回の最初の操作を持たせる。同じtask ID・同じ入力・同じ成果ハッシュなら、再現性確認を意図した場合を除き新規進捗として数えない。

失敗分類は少なくとも `not_executed`、`inventory_failed`、`dependency_failed`、`lean_failed`、`python_failed`、`artifact_failed`、`publication_blocked`、`stale_evidence` を区別する。

書き込み拒否時は対象操作・対象ファイル・拒否本文・提案差分を記録する。安全審査の回避を目的とする別経路の反復は行わない。許可された経路でもブロックされたら、適用可能なpatchと検証結果を保存し、必要な人手適用を明示する。

定期運用が外部サービスにある場合、現在の指示と実行実績を確認してから状態台帳を接続する。存在を確認せず「毎時運用済み」と記載しない。最初の失敗を未解決のまま、同種の新ブランチを量産しない。

## 5. 数学研究を再開する条件とテーマ

### W候補

対象は正の順序付き互いに素な組を正方形領域で数える

\[
W(J)=\sum_{\substack{1\le u,a\le J\\(u,a)=1}}\frac1{\varphi(4ua)}.
\]

候補 `W(J)=9/(2π²)(log J)²+O(log J)` はレビューで独立の紙上導出が得られたが、Leanでは未証明、新規性は未確立。以後は次の順で進める。

1. 元Agentの導出が保存されていれば取得し、レビューの独立導出と照合する。なければ未入手と記す。
2. Dahanの予測値と既存の多変数乗法的関数の評価を調べ、結果・手法・新しい帰結を分けて比較する。
3. 局所因子と有限畳み込み恒等式を最小Lean目標にする。
4. 絶対可和性、対数モーメント、尾部評価、Euler積の評価に必要なMathlib部品を棚卸しする。
5. 下流の篩への定数移送は別の主張として扱う。Wの3倍と、最適化後の係数の3^(1/3)倍を混同しない。

有限数値検証の増量だけで採用判断を進めない。Wの厳密化が既知と判明した場合は、再発見として記録し、明示的誤差や検証可能な新しい帰結があるかを判断する。1週間で解析部分すべての形式化を終えるとは約束しない。

### 未被覆集合・障害構造

Type I/IIの既知条件を基準に、固定shift・固定a・有限Jの不成功と、すべての解の不存在を区別する。小規模の事前固定範囲で、最小の障害証明書や両Typeの差を調べる。一般化できる補題、最小反例、方法の限界のいずれかが出た時点で記録し、無目的な範囲拡大は行わない。

- 量化・正値条件・定義が明確で、既知結果との差分を説明できる。
